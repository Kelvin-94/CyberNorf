# CyberNorf Roadmap

This roadmap is a planning baseline, not a promise of delivery dates. Items are complete only when code, tests, documentation, and review support that status.

**How to read it:** each phase lists what is **delivered** (checked, with the evidence that justifies the check) and what **remains** (unchecked, with the specific gap instead of a vague restatement). A `_Partial:_` note on an unchecked item means part of it ships but the item does not meet its own description yet. Capabilities that were built but were missing from earlier revisions of this file have been added to the phase where they belong rather than given a phase of their own.

Last aligned against the codebase: 2026-11-13.

## Phase 1 — Secure application foundation

**Delivered**

- [x] Authentication, MFA for privileged users, and secure session handling. Password sign-in with a 12-character minimum, eight-hour sliding sessions, TOTP with backup codes, and an optional single OpenID Connect provider (`src/server/auth/`). Because a privileged account cannot change tenant data without a second factor, every organization page carries a banner that names the requirement, says reads still work, links to `/account/security`, and puts enrollment at about a minute.
- [x] Organization membership and role/capability model. Four roles with deny-by-default capabilities (`src/server/authz/`). `OWNER` is the superuser tier — `ADMIN`'s capabilities plus five owner-only decisions, declared once as `OWNER_ONLY_CAPABILITIES` and asserted in `src/server/authz/roles.test.ts`: grant or revoke an `ADMIN`/`OWNER` membership, approve an engagement authorization, approve, suspend or revoke an agent, approve a non-human identity, and purge retained history. Services and pages call `can(role, capability)` rather than comparing `role === 'OWNER'`, so the tier has one definition and the separation between an administrator and an owner is visible in the capability list.
- [x] Non-human identity inventory, scoped machine credentials, and membership access reviews. _Implemented:_ identities of every kind carry an owner, criticality, lifecycle status and append-only timeline; machines start pending approval, are approved only by an owner, and receive one scoped, expiring, hash-stored bearer credential that only works on `/api/v1/identity/me`; access-review campaigns snapshot memberships and finalize retain/revoke decisions atomically (see [docs/IDENTITY_GOVERNANCE.md](docs/IDENTITY_GOVERNANCE.md)). Directory import, scheduled reviews and machine-credential recertification are not implemented.
- [x] Central policy enforcement on server-side operations. Every tenant route and server-rendered page resolves a `TenantContext` and checks capabilities; navigation only reflects them.
- [x] Tenant ownership checks and negative authorization tests. `tests/tenant-isolation.test.ts` plus per-module denial cases.
- [x] Personal API keys for automation. Scoped, expiring, hash-stored keys with their own authorization path (`src/server/authz/api-key.ts`, `/api/v1/me/api-keys`).
- [x] Audit events for authentication, permission changes, and privileged operations. Membership changes, data mutations, and access denials are hash-chained per organization; sign-in success and failure, second-factor verification, session ending, and two-factor disablement are recorded in the append-only `auth_events` table and shown to the account on `/account/security`.
- [x] CI checks for formatting, tests, dependency vulnerabilities, and secret leaks. `.github/workflows/ci.yml` runs `npm audit --audit-level=low`, format, lint, typecheck, migrations against a real PostgreSQL, the full test suite, a production build, a runtime audit against a live server, and a gitleaks history scan.
- [x] Structured logs with sensitive-value redaction. One JSON object per line on stdout with stable fields (`time`, `level`, `msg`, `service`, `env`), a `LOG_LEVEL` threshold, and child loggers for request-scoped fields (`src/server/logging/logger.ts`). Every record passes through the same redactor the audit trail uses before it is written, and logging never throws into the request it describes. Unhandled failures emit `request.unhandled_error` with the `requestId`; startup emits `server.started` with feature booleans only. Documented in [docs/LOGGING.md](docs/LOGGING.md) and covered by `logger.test.ts` and `errors.test.ts`. Access logs remain at the proxy so requests are not logged twice.

**Remaining**

- [ ] Secrets handling and safe configuration management. _Partial:_ every variable is validated at startup and by `npm run config:check`, which reports all problems at once, never prints values, and refuses a security-control downgrade. Secrets can be mounted as files through `SECRETS_DIR` (allow-listed variables, file-wins-over-environment, group/world-readable files refused) so Docker, Kubernetes and Vault-agent deliveries work without baking values into the environment. `npm run secrets:rotate` generates a replacement atomically with mode `0600`, refuses to overwrite without `--force`, never prints the value, and prints the rotation drill steps; `docs/SECRETS.md` carries the per-secret consequences (including that rotating `BETTER_AUTH_SECRET` logs everyone out and makes TOTP secrets unreadable). The effective configuration is fingerprinted at startup with an HMAC keyed by `BETTER_AUTH_SECRET` and stored in `system_settings`; a change is logged as `config.changed` and included in `server.started`. Remaining: no secrets-manager API client, rotation is assisted rather than scheduled, no rotation has been drilled against a real deployment, and the fingerprint records *that* the configuration changed and when, not what changed or who did it.

**Exit criteria:** sensitive routes have tested deny-by-default behavior; credentials are not committed to source; access boundaries are documented.

Status: exit criteria met for the implemented routes; secrets handling remains partial (see above), and structured logs now cover application faults and startup, not per-request access.

## Phase 2 — Defensive MVP

Build one complete, useful workflow rather than a wide collection of unfinished screens. Every item in this phase is delivered: the case workflow, detection input, alert delivery, evidence, indicators and export form an end-to-end path. Threat-intelligence enrichment is the notable remaining capability, and it belongs with the Phase 4 work rather than here.

**Delivered**

- [x] SOC case and incident workflow. Incident records with ownership, severity, notes, links to findings, and a forward-only lifecycle, every change audited (`INCIDENT_*` events). Evidence is attached through the evidence item below; promotion of an alert into a case is still absent.
- [x] Finding severity, rationale, and remediation tracking. Every finding carries a derived 0–100 risk score and a severity-based remediation deadline; the list filters and sorts on both; the dashboard reports overdue work, SLA compliance and mean time to resolve ([docs/FINDINGS.md](docs/FINDINGS.md)).
- [x] Audit history for important case changes. Incident and finding mutations append hash-chained events in the same transaction as the change.
- [x] Search constrained by authorization. Tenant-scoped, case-insensitive search over assets, findings, incidents and advisories, always composed with the caller's organization filter.
- [x] Endpoint monitoring and vulnerability intelligence. Agent enrollment with a one-time token and owner approval, signed runs (optional enforcement), heartbeat health, installed-package inventory, an imported advisory feed, and package-to-advisory matching that raises alerts.
- [x] Alert delivery with integrity. Notification channels with sealed signing secrets, HMAC-signed webhook transport, delivery records, and a cron-driven sweep with bounded retries.
- [x] Compliance and control evidence. Framework and control catalog, organization adoption, per-control attestation, evidence linked to real findings/incidents/assets, and agent checks mapped to controls.
- [x] Dashboards and reporting. Risk, SLA, agent health, and coverage summaries scoped to the organization.
- [x] Alert and IOC records with provenance. Indicators support domains, URLs, IPv4/IPv6, emails and MD5/SHA-256, stored normalised per tenant so repeated feed lines refresh one row instead of duplicating the observation history. Provenance covers source kind/name/URL/reference, first and last seen, confidence, expiry, actor and an append-only audit event; links attach an indicator to exactly one finding or incident with an `OBSERVED`/`REFERENCED` relation, are tenant-checked before write, and are covered by `tests/indicators.test.ts`. Enrichment is still absent and remains a later item.
- [x] Evidence attachment and integrity metadata. Files upload to `EVIDENCE_DIR` with a generated blob key (never a client-controlled path), are hashed while being written, size-limited mid-stream, and recorded with content type, size, SHA-256 and capture time. Verification re-reads the blob and reports `INTACT`/`MISMATCH`/`MISSING`, updates the row and appends an audit event; `npm run evidence:verify` sweeps a tenant or the whole database, and deletion removes the blob while refusing to strip the last evidence from an implemented control (`tests/evidence-files.test.ts`).
- [x] Search and export constrained by authorization. Search ships; export ships as `GET /api/v1/organizations/[orgSlug]/export`, gated by the `export.download` capability (owners, admins and analysts; not viewers), rate limited to five requests per five minutes, `Cache-Control: private, no-store`, and audited as `export.downloaded`. It carries business records, identity metadata without hashes, indicators and links, access reviews, quotas and the audit chain with its hashes; `EXPORT_VERSION` is 2 and credential fields are excluded. Covered by `tests/retention-export.test.ts`.
- [x] Unit and integration tests for expected and denied actions. 391 tests, all passing, including negative authorization and cross-tenant cases (`npm test`, 2026-11-12).

**Exit criteria:** a user can complete the chosen defensive workflow end-to-end, with authorization, audit, and documentation tested.

## Phase 3 — Operations and resilience

**Delivered**

- [x] Backup and restoration drills. `npm run db:restore-drill` dumps, restores, diffs tables/columns/constraints/triggers/migrations, re-verifies every audit chain with the application's own verifier, proves the append-only triggers still reject writes, and writes a JSON report. Documented in [DEPLOYMENT.md](docs/DEPLOYMENT.md#operating-it). A drill has to be run and its report retained to count as evidence.
- [x] Retention and deletion workflows. `data:retention` (dry-run first, audited purge) and `data:export`, both tested.
- [x] Deployment and rollback documentation. [DEPLOYMENT.md](docs/DEPLOYMENT.md), including upgrade and rollback behaviour for forward-only migrations.
- [x] Rate limits. Per-IP and per-user limits shared through PostgreSQL, with `Retry-After` and per-route budgets (`tests/rate-limit.test.ts`).
- [x] Liveness and readiness probes. `/api/health` never touches the database; `/api/ready` checks the database and compares applied migrations with the ones shipped in the image, answering `503` when the schema is behind the code.
- [x] Dependency vulnerability response, automated half. Dependabot with a cooldown and grouped development updates, plus `npm audit --audit-level=low` in CI and a gitleaks history scan.
- [x] Monitoring, alerting, and incident-response playbook. [INCIDENT_RESPONSE.md](docs/INCIDENT_RESPONSE.md) lists the detection sources with their exit codes and schedules (`/api/health` and `/api/ready` from outside the host, `evidence:verify`, `db:restore-drill`, audit verification, `config:check`, the `server.started`/`config.changed` startup lines, delivery records and capacity), the three-layer routing model, severity levels, and playbooks for host loss, database failure, evidence mismatch, secret compromise, authorization defects, delivery failure, account compromise and disk exhaustion. The product still ships no pager and no host-death notification: the external probe that supplies both is documented as a deployment requirement, and the gap is recorded.
- [x] Dependency update and vulnerability response process. [DEPENDENCY_RESPONSE.md](docs/DEPENDENCY_RESPONSE.md) adds the triage SLA (24 hours to decide and 72 hours to patch a critical), the decision record with `Patch`/`Mitigate`/`Accept`/`Not affected` values and mandatory review dates, the emergency patch procedure (including the full verification sequence), the customer advisory timings and content rules, and the monthly review. The known gaps are explicit: no SBOM, no automated base-image updates, and no advisory sent yet.

**Remaining**

- [x] Resource quotas. Per-tenant row quotas for assets, findings, incidents, identities, agents, indicators and API keys, plus evidence-storage megabytes, are enforced inside the create transaction from tier defaults with `organization_quotas` overrides (`src/server/services/quotas.ts`). Operators get `GET .../quotas` and an audited `npm run quota` CLI (`show`, `set --apply`) that writes `quota.override_changed`. Findings raised inside an agent run are budgeted instead of hard-failing the run: the run reads its remaining finding budget inside the transaction that stores it, keeps every host fact and check, creates findings only while budget remains, and reports `findingsSkippedForQuota` when it stops (`tests/agents.test.ts`). Concurrent execution jobs are capped per tenant by `EXECUTION_MAX_ACTIVE_JOBS` (default 20): dispatch counts `PENDING_REVIEW`, `QUEUED` and `RUNNING` jobs under a tenant advisory lock, so two requests cannot both take the last slot; over the cap no job row is written and the response is `429` with `Retry-After` (`tests/execution.test.ts`). Limitation: quotas count rows rather than CPU or bandwidth, and the job cap is per tenant, not per worker.
- [ ] Security review of API and tenant isolation. _Partial:_ [SECURITY_REVIEW.md](docs/SECURITY_REVIEW.md) records the internal pass over all 62 tenant route files (89 handlers under `/api/v1/organizations/[orgSlug]`), all wrapped by `withTenantApi`: 30 `GET`s of which 29 bind to a `.read` capability and one is the deliberate `export.download` exception, and every write method bound to a mutating capability. The pass found and fixed one real misbinding — evidence verification was a database write and audit event behind `compliance.read`, now `compliance.evidence` — and the earlier latent `dispatchEventById` trap is gone, replaced by `dispatchEventForOrganization(organizationId, eventId)`. Tenant resolution still comes from membership, writes by primary key still follow a scoped fetch, and there are no server actions or page-level database access. What keeps this open is independence: the reviewer is the author, so an external review with write access to a seeded two-tenant environment is still required, and the brief for it is in the same document.

**Exit criteria:** the team can detect important failures, recover data, and revoke compromised access.

## Phase 4 — Controlled execution and authorized testing

Do not begin this phase until the prior security foundation is implemented and reviewed.

- [x] Explicit engagement and target-scope model. `Engagement` carries a status and a time window, and `EngagementScopeEntry` holds `INCLUDE`/`EXCLUDE` rules over domains, IP addresses, CIDRs and URLs. Evaluation is deny-by-default and an exclusion always beats a broader inclusion (`src/server/domain/execution.ts`, `src/server/services/engagements.ts`).
- [x] Authorization records, exclusions, approval, and expiry. `EngagementAuthorization` needs a separate approver, and an expired, pending, rejected or revoked authorization denies dispatch. Requesting and approving are distinct actors, checked in the service rather than inferred from the capability.
- [x] Isolated workers with restricted network egress. `ExecutionWorker` declares its capabilities and an egress allowlist; dispatch selects only a worker whose allowlist covers the target and that has reported a heartbeat, so a registered but unheard-from worker is never picked.
- [x] Resource limits, job cancellation, and cleanup. Jobs carry a duration limit and a lease; cancellation is a request the worker honours, a later success report loses to it, and a repeated cancel request is idempotent. Cleanup closes reviews and queued jobs that can no longer progress.
- [x] Scope enforcement at job dispatch and execution time. Dispatch records the resolved target, approved address set and risk on the job; start re-evaluates the authorization and current scope and compares the live DNS answer to the recorded set, denying a job whose answer changed instead of following it. Redirects are evaluated as new targets.
- [x] Tests for redirects, DNS changes, expired scope, and cancellation. `tests/execution.test.ts` (13 integration tests) covers out-of-scope denial, exclusion precedence, missing and expired authorization, a changed DNS answer, a removed scope entry between dispatch and start, worker egress mismatch, cancellation winning over a later success, review separation, and cross-tenant reads. `src/server/domain/execution.test.ts` covers the pure scope engine, including redirect and CIDR cases.
- [x] Human review for higher-risk capabilities. A `HIGH`-risk job is created `PENDING_REVIEW` and can only be approved by someone other than its requester; rejection is terminal and never queues.

**Exit criteria:** out-of-scope execution is denied and verified by repeatable tests. Never use production or third-party systems as test targets without explicit authorization. _Met:_ every denial path above is asserted against a real database, and the execution surface is four declarative capabilities (`DNS_LOOKUP`, `HTTP_PROBE`, `TLS_INSPECTION`, `PORT_SCAN`) with no shell or arbitrary command channel. Reasoning in [ADR 0008](docs/decisions/0008-scoped-execution-and-evidence-packages.md).

## Phase 5 — Enterprise readiness

**Delivered**

- [x] Data residency for the shipped deployment model. The platform is self-hosted on the operator's host with a local database, so data residency is controlled by the operator and there are no subprocessors in the data path. Recorded in [DEPLOYMENT.md](docs/DEPLOYMENT.md). A hosted offering would reopen this.
- [x] Audit and evidence exports. `GET .../export/package` returns the full organization export wrapped in a signed manifest: per-document SHA-256 and byte length, organization, signer, key id and the audit-chain verdict at signing time, with an `HMAC-SHA256` signature over the canonical manifest. `npm run evidence:verify-package` verifies a file offline with the shared key and no database access, and issuing a package appends `export.package_signed` with the package id, key id and digests. Undeclared documents, changed documents, a wrong key id and a chain that was already broken are all rejected (`tests/evidence-package.test.ts`).

**Remaining**

- [ ] SSO and enterprise identity integration. _Partial:_ one OpenID Connect provider can be configured, with PKCE and verified-email linking; no SAML, SCIM, directory sync, or automatic de-provisioning.
- [ ] Administrative access reviews. _Partial:_ manual membership recertification with per-item retain/revoke decisions and atomic revocation exists, and a campaign can now name a reviewer: `reviewerId` is enforced rather than decorative, the reviewer must be an active `ADMIN` or `OWNER` and must not be the person who opened the campaign, and assignment, reassignment and clearing are each audited with the previous and new reviewer (`tests/access-review-reviewer.test.ts`). Still open: scheduling, privileged-access campaigns, and reviews of non-human credentials.
- [x] Customer-configurable retention. `organization_retention_policies` holds four independent windows — agent runs, alert deliveries, software inventory and execution jobs — with a 7–2555 day floor and ceiling. The console page under _Settings → Retention_ shows the effective and default policy and previews what each window would delete, per category (`src/app/app/[orgSlug]/settings/retention/page.tsx`); `GET`/`PUT .../settings/retention` read and save the policy, `GET .../retention/preview` counts what the stored or draft policy would delete without deleting anything, and `POST .../retention/purge` requires the literal `PURGE` confirmation plus the owner-only `retention.purge` capability and writes `retention.purged` with the cutoffs and the authoritative delete counts (`tests/retention-policy.test.ts`). `GET`/`POST /api/cron/retention` applies every saved policy once: only organizations with a stored policy are touched, each tenant is purged in its own transaction with a `SYSTEM` audit event, one tenant's failure does not stop the sweep, and the route answers `500` so a failing timer is visible (`enforceRetentionSchedules` in `src/server/services/retention.ts`, wired at `15 2 * * *` in [DEPLOYMENT.md](docs/DEPLOYMENT.md)). Running jobs, findings, incidents, evidence and audit events are outside the policy. Limitation: the sweep is a deployment timer rather than an in-process scheduler, so a deployment without the cron line still relies on the manual purge.
- [x] Documented data residency and subprocessors. [DEPLOYMENT.md](docs/DEPLOYMENT.md) records where tenant data lives for the shipped self-hosted model — the operator's host, database and backup region, with no vendor control plane, telemetry or licence check — the five outbound connections the stack can make and how each is turned off, and that there are no subprocessors by default: enabling SSO adds the identity provider and configuring an alert destination adds that receiver, both operator choices. This is documentation for the model that ships; a managed or multi-region offering would reopen it with a new data-flow review.
- [ ] Independent security assessment.
- [x] Availability and recovery targets based on tested capacity. [DEPLOYMENT.md](docs/DEPLOYMENT.md) states an RTO of 4 hours and an RPO of 24 hours for the single-host stack, including what each depends on: an off-host daily dump, a rebuild with `migrate`, and a passing drill before traffic returns. The restore drill was executed on 2026-11-12 and passed against the development dataset — 45 tables, 16 migrations, 177 constraints and 625 audit events recomputed, a 326.6 KiB archive, 2.7 s — and the report is archived as `docs/evidence/restore-drill-2026-11-12.json` instead of being quoted from memory. The measured duration is development-size evidence, not production evidence; the document says so and requires a production-size drill before the RTO is relied on. A tighter RPO needs WAL archiving or point-in-time recovery.
- [ ] Legal and privacy review for launch jurisdictions and target customers.

**Exit criteria:** product claims match verified controls, documented limitations, and actual operational capacity.

## Phase 6 — Zero Trust control plane

Delivered after Phase 5, because it needs the capability matrix, the audit chain and the tenant scoping that the earlier phases built. This is the phase where the platform stops only observing: it decides whether a request proceeds, and it can stop something. Reasoning in [ADR 0009](docs/decisions/0009-zero-trust-control-plane.md).

**Delivered**

- [x] A policy decision point that records the facts behind the verdict. `PolicyRule` is evaluated in ascending `priority` and the first rule whose every condition passes decides; no match is a `DENY`, and an unknown condition key invalidates the rule instead of being ignored. `PolicyDecision` stores the request context, the server-resolved facts, the risk score with its named factors, the matched rule and an explanation. The console has rule CRUD, a decision list, a decision detail page and an evaluation form (`src/server/domain/zero-trust.ts`, `src/server/services/policy.ts`, `src/app/app/[orgSlug]/policies/`).
- [x] Device enrolment, signed posture and derived trust. A device registers with an Ed25519 public key; a posture report is accepted only when its signature over the canonical `{ deviceId, collectedAt, checks }` verifies, and an unverified report is stored but cannot raise trust. Trust is derived from status, posture freshness, check results, management state and attestation, with a score ceiling per state, and admission reads the derived state rather than a stored label (`src/server/services/devices.ts`, `src/server/services/zero-trust-support.ts`).
- [x] Network connectors, segments and posture-gated admission. Connectors authenticate with a hashed bearer token, heartbeat into `ONLINE`/`DEGRADED`/`OFFLINE`, and carry a `failMode`. Admission resolves the zone from a stored CIDR segment, evaluates policy, and then applies the connector state: an unreachable connector with `CLOSED` refuses admission with `connector_unreachable_fail_closed`, while `OPEN` proceeds and records the unreachable connector. Segment change history, flow ingestion, connector rotation and a manual heartbeat round out the console (`src/server/services/network.ts`, `src/app/app/[orgSlug]/network/`).
- [x] Detections that carry their evidence. Five rules (`port_scan`, `quarantine_egress`, `ot_external_inbound`, `external_egress`, `bulk_transfer`) run over bounded flow batches, deduplicate on `(ruleKey, subjectKey)`, and store the supporting flow ids and a `freshUntil` so a stale detection is visibly stale rather than silently wrong.
- [x] Enforcement as a four-eyes, idempotent, expiring state machine. `REQUESTED → APPROVED → DISPATCHED → ACKNOWLEDGED → VERIFIED` with terminal `REJECTED`/`FAILED`/`EXPIRED`; the requester can never approve their own action, the four disruptive kinds additionally need a distinct second approver, `(organizationId, idempotencyKey)` makes a retry return the original, and a sweep expires unapproved requests and unacknowledged dispatches. Connectors acknowledge, fail or verify only actions bound to them (`src/server/services/enforcement.ts`, `src/app/app/[orgSlug]/enforcement/`).
- [x] Verified releases with staged rollout and per-device results. Publishing verifies the manifest signature against `ZERO_TRUST_PUBLISHER_KEYS` held in the environment, stores digest, compatibility and a `minVersion` floor, advances `DRAFT → CANARY → ROLLING → RELEASED`, rolls back to `ROLLED_BACK`, offers to devices idempotently on `(deviceId, releaseId)` and records install results (`src/server/services/updates.ts`, `src/app/app/[orgSlug]/updates/`).
- [x] Console coverage, capabilities, audit actions and tests. Five capability groups (`device.*`, `policy.*`, `network.*`, `enforcement.*`, `update.*`) with a Control section in the navigation; every mutation is audited in the same transaction, including machine-actor events under the `SYSTEM` actor. `src/server/domain/zero-trust.test.ts` covers the pure engine in 24 cases, and `tests/zero-trust-console.test.ts` covers signature verification, cross-device signature transplant, tenant isolation, connector heartbeat, fail-closed admission, deny-over-allow precedence and self-approval against a real database.

**Remaining**

- [ ] RADIUS and 802.1X with EAP-TLS, device discovery and VLAN assignment. _Partial:_ the admission decision, the zone outcome and the fail-mode behaviour exist and are recorded; the platform does not terminate 802.1X, does not hold a certificate authority and does not programme a switch.
- [ ] A decision point a gateway can call. _Partial:_ `POST .../policies/evaluate` requires `policy.manage` and `POST .../network/admission` requires `network.manage`, so both are tenant APIs; a connector cannot ask with its own token, and a decision is point-in-time rather than continuously re-evaluated when trust drops.
- [ ] Hardware-backed device identity. _Partial:_ `attestationKind` and `attestationVerified` are stored and gate `TRUSTED`, but no TPM or Secure Enclave quote is validated, and posture is submitted through `device.manage` rather than a device-authenticated channel — the signature binds the content to the device, not the transport.
- [ ] Network analytics and correlation. _Partial:_ five rule-based detections with supporting observations and telemetry freshness; there is no packet capture, deep inspection, TLS metadata, topology graph or learned baseline.
- [ ] Artifact delivery and rollback of an installed build. _Partial:_ manifest signatures, digests, anti-rollback, staged rollout and rollback-to-stop-offers ship; the platform does not serve artifacts, compute deltas, sign artifacts themselves or revert an installed build, and install results are reported through `update.manage` rather than by the device.

**Exit criteria:** every enforcement path is recorded with the facts behind it and cannot be triggered twice, silently, or by one person alone. _Met for the shipped surface:_ the integration tests assert the self-approval refusal, the idempotent retry, the fail-closed admission and the recorded explanation, and the remaining gaps are named above rather than implied.

## Release discipline

For each release:

1. Define scope and known limitations.
2. Review security-sensitive changes.
3. Run automated tests and relevant manual checks.
4. Confirm no secrets or sensitive data are included.
5. Publish installation, configuration, upgrade, and rollback instructions.
6. Record unresolved risks and follow-up owners.

Do not label the platform production-ready or compliant with a framework merely because a roadmap item or documentation file exists.
